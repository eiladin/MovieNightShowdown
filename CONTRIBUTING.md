# Contributing to Movie Night Showdown

This is a small, self-hosted project, so the process here is deliberately
light. This page walks you through getting the app running locally, the checks
your change has to pass, and the handful of conventions we keep so that the
release notes and the architecture stay coherent.

You don't need a Jellyfin server to work on this. Jellyfin is one movie source
among peers, and the app runs perfectly well against streaming sources alone —
or against neither, in which case it serves an in-app setup guide explaining
what's missing.

## Getting set up

You'll need Go — the version is pinned in `go.mod` — and Node 24. Docker is
optional, but it's the easiest way to run the whole thing end to end.

The backend and the frontend can run separately while you're working:

```sh
# Backend
go build ./... && go run .

# Frontend, with hot reload against a running backend
cd web && npm install && npm run dev
```

Or you can run it the way it ships:

```sh
docker compose up --build
```

One thing to know before you run a production-style build: the Go server serves
the frontend from `web/dist` and embeds it into the binary, so `go build` fails
on a clean checkout until that directory exists. Run `cd web && npm run build`
first. The Dockerfile does this for you, which is why `docker compose up` needs
no such step.

At least one movie source has to be configured before the app can deal a deck —
Jellyfin, a TMDB read token for streaming services, or both. The environment
variables are documented in [docs/INSTALL.md](docs/INSTALL.md).

## Running the checks

Both suites have to pass before a pull request can merge. CI runs exactly these
commands, so if you run them locally you'll see precisely what CI sees:

```sh
gofmt -l .            # must print nothing
go build ./...
go vet ./...
go test ./...
golangci-lint run ./...
```

```sh
cd web
npm run lint
npx tsc -b
npm test
npm run build
```

`golangci-lint` is configured in [`.golangci.yml`](.golangci.yml) and is tuned
to find bugs rather than style problems. `errcheck` is deliberately off, because
every unchecked error in this codebase is an intentional discard. If the linter
flags something you believe is correct, say so in the pull request rather than
adding a blanket suppression — the config sits at zero findings today, and
that's what makes the next one worth reading.

## Opening a pull request

`main` is protected. Work on a branch, open a pull request, and let the three
required checks — `go`, `web`, and `build` — go green.

Pull requests are squash-merged, so the pull request title becomes the commit
message on `main`. Give it the same shape as a commit:

- Commit messages follow [Conventional Commits](https://www.conventionalcommits.org)
  — `feat:`, `fix:`, `docs:`, `chore:`, `refactor:`, `test:`, `perf:`, `ci:`.
  The release notes are generated from the commit range since the previous tag,
  so the prefix is what determines how your change is described to users.

## Understanding the architecture

[`AGENTS.md`](AGENTS.md) in the repository root is the fullest description of
how the pieces fit together and which invariants matter. It's written for coding
agents, but it's accurate and readable for humans — read it before a non-trivial
change. The `CLAUDE.md` beside it is a one-line import of that file and nothing
more.

Two rules are worth repeating here, because they're the ones a well-meaning
patch breaks most often:

- **Sources are enumerated server-side.** `GET /api/library/filters` reports the
  sources this deployment can query, and the frontend renders exactly that list.
  Don't add a client-side list of streaming services — a deployment can be
  configured with any TMDB watch provider, so no fixed list is correct.
- **Capabilities are declared, not inferred.** A source states what it supports
  by implementing an optional interface in `server/source.go`, and that answer
  travels to the client on `SourceDescriptor`. Never branch on a source id to
  decide what a source can do, on either side.

## Regenerating the screenshots

`docs/screenshots/01-landing.png` through `05-result.png` are generated by a
deterministic pipeline that runs the real app against a mock Jellyfin server
full of fictional placeholder movies. It needs no real server and no personal
data:

```sh
make screenshots
```

`docs/screenshots/hero.png` is hand-curated and the pipeline doesn't touch it.
See [`scripts/screenshots/README.md`](scripts/screenshots/README.md) for how the
pipeline works and how to regenerate the placeholder poster art.

## Reporting a bug

Open an issue describing what you expected, what happened instead, and the
relevant server log lines. Redact any API key or token before you paste logs.

If you think you've found a security problem, don't open an issue — see
[SECURITY.md](SECURITY.md) for the private reporting channel.

If you get stuck on any of this, open a draft pull request or an issue and ask.
A half-finished branch with a question attached is a perfectly good way to
start.
